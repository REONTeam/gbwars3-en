# Map AI tactical helper spans (the project)

the project closes the three residual Bank `$0D` source gaps between the already-owned action dispatcher/staging code and the `$4B91` capture-target-mask builder:

- `$44EE-$469E` — 433 bytes
- `$46B7-$471C` — 102 bytes
- `$4749-$4A42` — 762 bytes

Together these are 1,297 retail bytes after the project splits `$4A43-$4B90` into symbolic unit-type profile data. They are kept as exact `db` source while the target-ranking/scoring scratch fields remain only partially understood. Directly called entry points are exposed as labels so later work can convert callers away from raw addresses without pretending to know more than the behavior proves.

Four action-staging identities are independently proven inside the first span. `$44EE` ultimately writes action 3 and calls the already-source-owned direct-attack executor; `$4654`, `$4665`, and `$468B` stage action IDs 1, 2, and 5 respectively before invoking the common dispatcher. Those are therefore named as direct attack, capture, development, and area-attack staging helpers. Other entries retain address-oriented `MapAI_TacticalHelper*` names until their scoring/selection contracts are traced.

The remaining `$4749-$4A42` family is reached directly from the project bridge/direct-attack planner and contains repeated candidate scans, UnitData queries, list/scratch manipulation and comparisons. It is safe to classify this span as tactical target search/scoring, but not yet safe to assign narrower policy names to each helper.


the project makes `engine/map/ai/map_ai_tactical_priority_data.asm` the sole owner of `$4A43-$4B90`; those 334 bytes are now two symbolic 52-entry unit-type profile pointer tables plus zero-terminated lists rather than opaque scorer bytes.
